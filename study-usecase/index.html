Oui : prenez les trois, mais rendez-les disponibles à la demande

Décision claire : OUI pour installer et exposer les trois ; NON pour appeler les trois à chaque tâche. Leur coexistence MCP est prouvée et leurs capacités de code sont distinctes. En revanche, ce benchmark ne prouve pas que Graphify et OpenWiki améliorent chaque réponse : dans les essais trio, l’agent a souvent choisi Serena et obtenu la même qualité. La bonne décision est donc trois capacités disponibles, une source choisie d’abord, puis escalade seulement si nécessaire.

Pile opérationnelle proposée : agent de code = Serena + Ponytail + RTK ; agent d’architecture = Graphify + OpenWiki, avec Serena pour confirmer ; Claude‑mem traverse les rôles comme mémoire inter-session. OpenWiki est actualisé après les changements qui méritent une explication durable.

Le test principal est désormais aligné sur la promesse de chaque outil : architecture, refactoring multi-fichiers et documentation durable. Chaque scénario est exécuté trois fois avec le spécialiste seul, puis trois fois avec les trois sources disponibles. Les traces ont subi deux audits contradictoires par claude -p.

Résultat principal : la qualité est équivalente quand les runs terminent, mais le coût dépend fortement du routage. Graphify seul et le trio donnent pratiquement la même carte architecturale. Dépôt réel Pallets Click, source figée au commit 36baa15, 12 674 lignes Python. Modèle gpt-5.6-sol, effort medium, contexte neuf. Pour chaque rôle, le texte de tâche est identique entre spécialiste et trio ; seul le préfixe d’accès diffère nécessairement : une source imposée contre trois sources routables. Trois répétitions par cellule, soit 18 runs.

Graphify : qualité démontrée, gain non démontré

Le graphe seul restitue 19–20 faits architecturaux sur 20. Mais le trio, routé surtout vers Serena, fait aussi bien avec moins de tokens frais. Sur ce dépôt et cette question, Graphify n’établit donc pas une supériorité de vitesse ou de tokens.

Serena : preuve opérationnelle forte

Cinq worktrees contiennent exactement les 3 fichiers attendus et 9 remplacements, sans erreur de diff ; 104 tests passent sur chacun. Un sixième run seul s’est bloqué avant édition et reste compté comme échec de fiabilité.

OpenWiki : lecture très compacte après génération

Le corpus pré-généré répond 18/18 avec 2 lectures et 7 531 tokens frais en moyenne. Avec le trio, le routeur explore Serena : même score, +45 % de temps et +287 % de tokens frais. Cela mesure le corpus, pas un appel MCP de requête OpenWiki.

Preuve qu’ils cohabitent — et frottement découvert

Le test MCP direct a démarré les trois serveurs simultanément et reçu les réponses de leurs 10 + 29 + 6 outils en 2,07 s : statistiques Graphify, symbole Command/main via Serena, cycle update OpenWiki. La coexistence technique est établie pour ce snapshot : aucun conflit de nom ni de chemin n’a été observé.

Ils ne se “marchent” pas dessus, mais il faut ignorer leurs artefacts. Sans .gitignore/.openwikiignore, OpenWiki a considéré graphify-out/, .serena/ et les configs d’intégration non suivies comme des changements. Après exclusion et commit de la configuration, changedPaths devient vide. Dans ce snapshot, le MCP OpenWiki ouvre néanmoins encore un run et accepte un plan à zéro page au lieu de renvoyer le noop annoncé : c’est un coût d’orchestration réel à surveiller.

Verdict exécutif

Oui, prenez les trois comme capacités disponibles. Le smoke test prouve qu’ils cohabitent. La valeur opérationnelle de Serena est directement démontrée par les diffs et tests. Graphify et le wiki OpenWiki réussissent leurs scénarios de compréhension, mais le trio piloté par l’agent obtient la même qualité en utilisant majoritairement Serena : ce benchmark ne prouve ni leur nécessité systématique ni un gain universel. La recommandation est donc un choix d’architecture fondé sur leurs fonctions distinctes, avec activation à la demande.

La formule exacte issue du code : OpenWiki explique et mémorise sous forme de pages sourcées ; Graphify modélise et traverse des relations ; Serena résout et agit sur les symboles du code courant.

La vraie architecture : activer les capacités selon le rôle de l’agent

Règle centrale : la pile possède six capacités, mais une tâche ne doit pas charger six résultats. Serena agit sur le code, Graphify cartographie, OpenWiki documente, Ponytail limite le code au nécessaire, RTK compacte les sorties shell et Claude‑mem restitue l’historique utile entre sessions.

Ponytail · discipline de solution

Il ne remplace ni Serena ni les tests. Sa ladder demande d’abord si le code doit exister, peut être réutilisé, fourni par la stdlib ou la plateforme, puis choisit le minimum qui fonctionne sans sacrifier sécurité, validation ou accessibilité. Source officielle.

RTK · hygiène du contexte shell

Proxy Rust qui filtre les sorties de commandes courantes avant leur entrée dans le contexte : fichiers, recherche, Git, tests et Docker. Ses économies annoncées portent sur la sortie Bash, pas directement sur la facture totale. Source officielle.

Claude‑mem · mémoire épisodique

Capture les observations et résumés de sessions, puis expose une récupération progressive par recherche, chronologie et détails. Il complète OpenWiki : Claude‑mem se souvient de ce qui s’est passé ; OpenWiki explique ce que le système est censé faire. Source officielle.

Relier

Forces et faiblesses observées dans le code

Graphify — forces

  • Extraction code locale et déterministe, très large éventail de grammaires Tree-sitter.
  • Modèle relationnel directement exploitable : BFS/DFS, voisins, chemins, communautés et blast radius.
  • Budgets explicites de sortie MCP, par défaut 2 000 tokens pour les requêtes.
  • Mise à jour incrémentale par source avec séparation des couches AST et sémantique.
  • Arêtes étiquetées EXTRACTED, INFERRED ou AMBIGUOUS.

Graphify — faiblesses

  • Un extracteur Tree-sitter n’est pas un compilateur complet : la résolution inter-fichiers utilise aussi des heuristiques et peut rester ambiguë.
  • Le graphe persistant devient faux s’il n’est pas actualisé après les changements.
  • Le wiki exporté est assemblé depuis communautés/hubs : utile comme catalogue, moins apte à expliquer les intentions métier qu’un auteur agentique.
  • Aucun outil MCP ne renomme, déplace ou corrige le code.
  • Les contenus non-code et les noms riches de communautés peuvent nécessiter un modèle, donc coût et risque d’inférence.

Serena — forces

  • Le meilleur niveau de précision opérationnelle des trois : symboles, références, implémentations, déclarations et diagnostics.
  • Renommage sémantique multi-fichier via le WorkspaceEdit produit par le serveur de langage.
  • Éditions au niveau du symbole, suppression sûre et diagnostics après édition.
  • Backend JetBrains plus riche : move, inline, inspections, hiérarchie, debug.
  • Réponses raccourcies progressivement et limite de caractères configurable.

Serena — faiblesses

  • La qualité dépend du serveur de langage, de sa configuration et de la qualité sémantique propre à chaque langage.
  • Démarrage/indexation et installation de serveurs peuvent être plus lourds qu’une recherche textuelle.
  • Ne fabrique pas nativement une vue macro durable ou un manuel d’architecture complet.
  • Les capacités JetBrains avancées nécessitent le plugin/IDE correspondant ; plusieurs outils sont marqués optionnels ou bêta.
  • Sa surface d’édition et de shell est puissante : le contrôle d’autorisation doit venir du client/orchestrateur.

OpenWiki — forces

  • Excellent format humain/agent pour le « comment » et le « pourquoi » : pages ciblées, index et liens.
  • Claims reliées à des preuves de dépôt versionnées, avec détection déterministe de preuves obsolètes ou introuvables.
  • Runs reprenables, file de pages durable, écritures confinées à openwiki/, validation des liens/Mermaid/provenance.
  • Les mises à jour acceptent un plan à zéro page et les décisions de Claims clairsemées limitent les répétitions.
  • Sources personnelles et runtime variées, notamment LangSmith pour relier comportement observé et code.

OpenWiki — faiblesses

  • La génération native est agentique : c’est la brique la plus susceptible de consommer temps et tokens à l’initialisation.
  • Une Claim « grounded » garantit une preuve versionnée et sa fraîcheur, pas automatiquement que la phrase implique correctement cette preuve : l’auteur reste un modèle/hôte.
  • Les Claims repository ne couvrent pas les faits issus des connecteurs personnels.
  • Son graphe visuel est construit à partir des liens Markdown, pas des appels, imports ou héritages du code.
  • Il documente le code mais n’est ni un moteur LSP ni un outil de refactoring.
  • Dans le test host-MCP, un dépôt sans chemin changé a encore ouvert un run à zéro page au lieu de retourner noop.

Où sont-ils concurrents, exactement ?

Graphify ↔ OpenWiki

Concurrence réelle sur le bootstrap d’un dépôt inconnu, la mémoire persistante, la navigation globale, la production d’un wiki et une visualisation en graphe.

Différence décisive : le graphe Graphify encode des entités et relations extraites du corpus ; le graphe OpenWiki encode les liens entre pages rédigées. Le premier répond mieux à « qui dépend de quoi ? », le second à « comment ce système est-il censé fonctionner ? ».

Graphify ↔ Serena

Concurrence limitée sur la localisation de symboles, usages et dépendances.

Différence décisive : Graphify interroge un snapshot relationnel large, possiblement inféré ; Serena interroge l’état sémantique courant du projet via un serveur de langage et peut appliquer le refactoring. Le graphe cible la zone ; Serena confirme et opère.

OpenWiki ↔ Serena

Très peu de concurrence : tous deux peuvent lire/rechercher des fichiers et garder de la mémoire, mais ce sont des moyens secondaires.

Différence décisive : OpenWiki fabrique une connaissance durable à consulter plus tard ; Serena ferme la boucle perception–action sur le code courant. L’un ne remplace pas l’autre.

Les trois vont-ils gaspiller des tokens ?

Installés sur disque : non. Exposés tous les trois à l’agent : parfois. Les schémas d’outils, les résultats renvoyés et l’exploration supplémentaire peuvent grossir le contexte. Ce n’est toutefois pas automatique : sur le test architecture et le refactoring terminé, le trio a consommé moins de tokens frais en moyenne ; sur la lecture du wiki, il en a consommé +287 % sans gain de score.

Conclusion tokens précise. Il n’existe pas de pénalité fixe « trois outils ». L’effet observé va de −29 % de tokens frais sur l’architecture à +287 % sur le mémo wiki. Règle de routage simple

Commencer par une seule source : symbole/édition → Serena ; explication déjà documentée → page OpenWiki ; requête explicite de chemin/relations/impact → Graphify. Ajouter une deuxième source seulement si la première laisse un manque vérifiable.

Après modification

  • Tests et diagnostics d’abord.
  • graphify update . pour remettre le snapshot structurel à jour sans modèle.
  • openwiki --update seulement si le changement invalide une explication durable ou si le cycle planifié le demande ; ignorer graphify-out/ et .serena/, puis traiter un plan vide sans génération.

Preuves particulièrement discriminantes

  • Graphify sépare explicitement le code AST de la passe LLM documentaire.
  • Graphify possède bien son propre export wiki : le chevauchement avec OpenWiki n’est donc pas imaginaire.
